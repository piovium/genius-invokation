**结论与适用边界**

按最终裁定，327 个顶层 ID 中，**16 个涉及手写或数值适配，311 个为线上定义复用候选**。后者包含尚需整组版本/依赖核验的项目，不代表全部通过行为验证。16 个顶层 ID 为 `1607, 2205, 2404, 2601, 311205, 311305, 311306, 312015, 312016, 321006, 321008, 322003, 322004, 322008, 332015, 332016`；实际覆盖定义数可不同，例如终末只需修改依赖状态 `301102` 的增伤条件。

明确保留玩家选择的顶层 ID 为 **322008 立本、332015 深渊的呼唤、332016 愚人众的阴谋、321006 西风大教堂**，全部使用 `selectOption`。其他问答提出的目标自选、效果选序、强制重建和区域改造均不纳入最终范围。

现有 profile 管线可以承载“固定历史版本 + 同 ID GTS 覆盖 + 静态展示覆盖”。但不能直接把已有研究的 `preferredVersion` 拼成一个可发布的实体牌 profile：逐牌推荐之间存在依赖版本冲突；部分差异来自描述拆分或资料字段；实体数据的 `qaList` 还明确规定了正文比对没有覆盖的玩家选择和实体化改动。

研究原始范围有 327 个顶层 ID：284 个有完整推荐，43 个没有。284 是“研究比较范围内成立”，不是 284 个已经验证可原样运行的实现；其中 6 个依赖缺描述通配，原有 8 张补充手写候选经本次裁定保留 4 张、撤销 4 张。43 个失败结果也不等于 43 张必须重写。

生成时的字段对应关系为：实体 code/记录 ID/完整 cardNo 仅作来源，线上 ID 作定义键；`hp` 对应角色生命值；`skillCostList` 对应每个技能费用；行动牌的 `element` 与 `energyCost` 合并为打出费用，充能不能计入骰子总数；`skillType` 对应技能类别；`effectDesc` 与 `skillDesc` 对应正文。源里的 `{{…}}` 和配件名称不能直接作为线上 `$[C…]`/`$[S…]` 引用使用，需要按映射转换。背景故事、产品信息不进入运行规则；QA 单独保留裁定依据。角色最大充能不在原比较的独立字段范围内，费用改动时必须额外核对。

**版本选择与全局依赖统一**

附录逐条保留 284 个原始推荐：229 项为 v7.2.0，55 项为其他版本；发布时还要剔除上述无来源兼容项、应用手写覆盖和资料裁定。`matchedVersions` 只表示自身匹配，不能代替 `preferredGraph` 的完整子树判定。没有推荐版本的牌保持空缺，不能把最近线上版本冒充匹配版本。

本次用当前 analyzer 的 2,316 条依赖记录检查 284 项合并结果，有 **44 个 ID 获得不一致的传播版本**。实际调用现有 resolver，首先报错：`1101 -> 11013` 要 v5.4.0，而 `211011 -> 11013` 要 v7.2.0。即使两个版本的运行定义相同，resolver 仍比较版本号并拒绝冲突。

可行的数据方案是显式固定共享技能与配件版本，而不是改 resolver 为后写覆盖。附录为这 44 个 ID 提供“采用所属角色推荐版本”的统一候选；其中 38 个有对应版本的 exact/near 节点证据，6 个内部节点没有独立静态研究证据，随所属技能实现核对。该方案只解决传播冲突，不等于完成所有运行语义验证。新增手写牌与补回角色后仍应重新计算闭包。

已实际验证这一候选：284 个根加 44 个显式依赖，共 328 项，传播后为 730 个 ID；现有已构建 core/data 的 resolver 与 `registry.resolve(resolver)` 均成功，284 个顶层定义没有缺失。这不是完整 preset 编译或游戏行为测试。

另需纠正一项原研究误判：**323003 红羽团扇改选 v6.5.0，并显式固定旧状态 302303 为 v6.5.0**。实体增益仅限本回合；v6.6.0 起的高效切换/敏捷切换没有这一期限，并可积层，不能作为措辞相同处理。v6.5.0 的旧 GTS 使用 `oneDuration` 的 RedFeatherFanStatus，可以复用，无须另写同样效果。该修正加入后 329 项显式选择仍能解析，红羽团扇实际命中 until v6.5.0 定义。当前 analyzer 对 323003 只记录最新的 169/170 依赖，漏掉历史实现的 302303；这也说明选历史版本时必须审查旧 GTS 的依赖，不能只靠当前 analyzer 自动传播。

当前 resolver 支持给依赖 ID 显式指定版本，从而阻止其他根向它传播；但一个 ID 在整局只会解析成一个定义，不支持同一配件按来源角色采用不同历史版本。遇到真实语义不相容时，应给该 ID 写统一的实体版本，或拆成内部不同 ID 并同步引用，不能仅凭根级研究图保留两个答案。

**所有手写交互统一采用 selectOption 的约束**

现有协议支持提示文本、带唯一非空 `key` 的文本选项，返回 `selectedIndex`；服务端验证索引，GTS 通过 `on selectOption` 读取 `selectedKey`。调用返回 `void`，不是可 `await` 得到答案的表达式。[skill_context.ts](../../packages/core/src/runtime/skill_context.ts)、[skill_executor.ts](../../packages/core/src/skill_executor.ts)、[rpc.proto](../../proto/rpc.proto) 是依据。

每个手写选择应在请求前建立有效的后续响应者，使用 `via.caller.id` 和阶段键定位本次选择，在响应事件里才执行依赖结果的效果。不要在发起请求后立即扣完使用次数、销毁响应者或执行尚未决定的分支。两个立本或两座西风大教堂等同名实例不能仅按定义 ID 匹配。需要选择多个对象时（如立本的骰子），采用合法组合单选或分步单选，不需要把 RPC 改成自由文本。

最终保留的手写玩家选择为立本收集骰子、深渊的呼唤/愚人众的阴谋双边声明元素、西风大教堂满血触发选择，全部使用 `selectOption`。后续手写逻辑若确实引入其他玩家选择，也适用这一要求；不得据此恢复已否决的选序或目标选择。选项只有一个时仍须区分“规则自动确定”与“玩家可以拒绝”，不能删除后者的拒绝选项。

| 场景 | 候选与阶段 | 必须保留的规则 |
| --- | --- | --- |
| 立本 | 以骰种/数量形成稳定组合键，0～剩余容量个，本次每种最多一个，万能独立计数；或逐个选择并提供“结束” | 累计上限 3，历史骰种不限制本次候选；不可自动贪心吸收，选择完成后统一移除与记录 |
| 深渊的呼唤 / 愚人众的阴谋 | 我方先选六种元素对之一，对方再选其中一种 | 先后两次 RPC；第二次提示必须含已声明的两种元素；最终生成的阵营不能因回答者变成对方而颠倒 |
| 西风大教堂（QA-03） | 满血时“触发 / 不触发” | 确认后才消耗次数；望舒客栈、珊瑚宫分别按 QA-28、QA-38 自动不触发 |

`selectOption(prompt, options)` 高层入口固定请求 `self.who`，没有 `who` 参数；但当前公开的 `emitEvent("requestSelectOption", skillInfo, who, prompt, options)` 能指定对方，并最终进入同一个 RPC。可在手写 GTS 中采用此通路并保持同等候选校验，或让对方拥有的临时协调状态调用高层方法。前者不需要改协议，后者要处理协调状态生命周期与 `listenTo all`。因此“对方选择”不是 RPC 本身不支持，而是高层便捷接口不足。

现有对方通知只包含“某玩家已选择”，不公开提示、候选和答案。公开声明不能依赖这条通知传达；应在第二次请求、后续实体状态或新增公开通知中明确展示。秘密选择仍应按现有可见性处理。

QA-50、QA-51、QA-52、QA-57 分别保留线上受击/切换时序、砂糖重建行为、诺艾尔及行秋伤害计算。QA-54/60/77 保留蛙和兔兔伯爵的线上分类与减伤顺序；QA-55/56/78/79/85/86 仅重复 QA-02 的护盾通则，均引用“不采纳、沿用线上”的裁定。QA-58/62/69/70 四组协同效果、QA-61 的血梅香/披萨均保持线上顺序。QA-59 不新增冰/水附魔选择，QA-63 不新增减费选序；因此撤回因这些未采纳规则提出的同步伤害暂停、费用选择与预计算改造要求。

QA-64 保留温迪线上重建行为，QA-65/80 整体保留线上伤害及免于击倒时序，QA-66/81 对岩盔直接应用线上行为、不做合并调整。QA-67、QA-68/74/82、QA-71/83 也已决定保持线上。至此，问答中所有玩家自主选择效果结算顺序的提案均未采纳；本报告不再要求通用选序调度器、同步伤害暂停或费用预计算重构。已确认的卡牌内选择仍使用 selectOption。
